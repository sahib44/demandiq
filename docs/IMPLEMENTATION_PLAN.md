## Architecture and component responsibilities

- Python 3.12 packages under `ml/` provide independently testable analytical logic. `ml/data/` owns acquisition, validation, cleaning, quality reports and weekly facts/selection; `ml/features/` owns causal historical/calendar predictors; `ml/models/` owns baselines, configuration and fitted preprocessing/regressors; `ml/evaluation/` owns chronological splits, metrics, uncertainty, figures and the final-test ledger. `ml/inventory/` owns validated assumptions/stock state, order constraints, chronological simulation and reconciled static figures.
- `scripts/` provides thin command-line entry points. Dataset imports must work without an API process; structured logs contain counts and identifiers for artifacts, never transaction or customer records.
- `ml/pipelines/modeling.py` separates pre-test candidate selection/calibration/refitting from once-only final evaluation. `python -m scripts.train` publishes frozen artifacts; `python -m scripts.evaluate` checks them before a dataset-scoped test reservation and reuses verified completed results. Local JSON/Parquet tracking avoids an experiment-tracking service dependency.
- `ml/pipelines/inventory.py` verifies completed Phase 3/ledger lineage, derives stock/error assumptions only from pretest facts/calibration, snapshots JSON scenarios, runs five policies with common inputs and publishes hash-verified analytical results. `python -m scripts.run_inventory` runs default, lead-time and explicitly exploratory economic sensitivities without loading model serializers or changing forecasting choices.
- `backend/app/db/` owns SQLAlchemy models and transactional metadata persistence. Alembic owns database changes. PostgreSQL stores metadata and references; large data files stay outside Git.
- Phase 5 implements FastAPI route validation, service orchestration and a PostgreSQL-backed worker. Route handlers call services, not ML implementations directly. Worker claims use `FOR UPDATE SKIP LOCKED`, leases, idempotency keys, bounded retries and recovery of expired leases.
- Phase 6 adds a Vite React/TypeScript client with typed API calls. Pages: executive overview, data quality, forecast explorer, inventory planner, scenario comparison and model performance. Shared accessible components, hooks and types keep page logic focused. Charts display measured data; CSV exports come from real persisted results.
- Full local Compose now provides PostgreSQL, initialization/migrations, API, durable worker and Nginx/React. The optional demo profile activates a verified historical bundle through HTTP jobs. No hosted Site or cloud deployment is in scope.

## Data pipeline

1. Download the official UCI ZIP with bounded network retries, timeouts, byte limits and safe extraction of the expected XLSX only. Record URL, license/citation and SHA-256 digests. Cache validation and atomic writes prevent silent corruption; a supplied expected checksum detects upstream changes.
2. Accept local XLSX/CSV input with the eight required columns. Enforce typed normalized output; preserve row numbers for all decisions. Parse Excel datetimes or explicitly documented day-first strings. Do not guess ambiguous US date formats or time zones.
3. Remove exact source duplicates before normalization and record their source rows. Do not collapse merely similar transactions. Normalize identifiers and whitespace; flag missing descriptions/customer IDs/countries without inventing their values. Missing invoice/product identifiers, product identifiers exceeding the database's 128-character limit, unparseable dates, nonintegral/zero quantities, nonfinite/nonpositive prices and nonmerchandise codes are quarantined with reasons.
4. Classify negative C-prefixed invoices as cancellations; quarantine positive C-prefixed invoices with a sign-anomaly reason. Classify other negative quantities as returns. Positive purchases form the future gross-demand source. Preserve signed quantities. Do not match credits to original orders without evidence or subtract cancellations twice.
5. Hash available customer IDs with a domain-separated one-way digest; no raw customer identifier enters processed artifacts, database records, logs or committed fixtures. Raw public source files remain ignored locally. Deterministic pseudonyms allow later unique-customer counts but are still sensitive local artifacts and must not be exposed publicly.
6. Produce typed Zstandard Parquet files for purchases, cancellations, returns and a privacy-safe row audit of every exclusion/flag/transformation; deterministic JSON quality report and manifest include counts before/after each stage and input/configuration/version hashes. Publish a complete dataset directory atomically; identical input/configuration reuses and verifies artifacts. Failure must leave no partial completed dataset.
7. Optionally persist metadata, quality report and product catalog together in one idempotent PostgreSQL transaction after files succeed. Import can run offline without a database; later persistence must be safely retryable.

## Forecasting and ML pipelines

Phase 2 defines explicit chronological training/validation/test dates before ranking products. Default `TOP_PRODUCTS=50` is configurable and ranking uses training-period positive volume only, with deterministic tie-breaking. Build continuous Monday-start weekly panels, retaining gross sales, returns, net units, revenue, transaction counts, distinct known customers and average price; document partial edge weeks. Gross positive units are the initial target. Fit preprocessing within each fold. Lag all historical covariates and rolling windows. Add at least three expanding folds when feasible; declare insufficient seasonal history rather than pretending a yearly baseline is supported.

The implemented Phase 2 config fixes training 2010-12-06–2011-07-11, validation 2011-07-18–2011-10-03 and reserved test 2011-10-10–2011-11-28 (all week starts). Three four-week expanding folds reselect products from each training boundary, then freeze that cohort within the fold. The runner loads only pre-test transactions; no test target, feature or metric enters Phase 2 artifacts. It records separate returned/cancelled units, net units and purchase revenue. Missing selling price and undefined historical rates remain null. Seasonal naive uses an explicitly assumed four-week recurrence; annual 52-week recurrence is unsupported by the initial 32 training weeks. See [the full forecasting protocol](FORECASTING_METHODOLOGY.md).

Phase 2 artifacts live under a source/configuration/runtime-derived `data/phase2/<run_id>`: weekly facts, fold-scoped products/features, validation predictions, training volumes, metrics, figures and immutable manifests. `scripts/run_phase2.py` is the CLI boundary. Phase 5 now persists training-scoped weekly facts and model/forecast/scenario lineage; no speculative future tables were added to Phase 1. All figures use pinned Matplotlib and the tested parser version rather than an interactive frontend; the dashboard remains Phase 6.

Phase 3 implements Ridge, Random Forest and XGBoost, each compared against naive, four-week mean and four-week seasonal naive. Random Forest is the specification's permitted tree option; it replaces the tentative HistGradientBoosting choice because the modest panel fits economically and exposes native feature importance. Two candidates per family are declared before fitting. Selection minimizes pooled selection-validation WAPE, then MAE and identifier, with an MAE fallback for undefined WAPE. The best ML family and best overall method are recorded separately.

The first two expanding folds (validation 2011-07-18–2011-09-05) determine candidates and recommendations. The third fold (2011-09-12–2011-10-03) is reserved for out-of-sample residual calibration after selection is frozen. Each fold fits median imputation/missingness indicators and product one-hot categories on training only; Ridge also fits scaling. Supervised fitting excludes the initial twelve lookback weeks. Candidate, selection and calibration metrics are separate artifacts. The final cohort and models refit through 2011-10-03, then remain fixed across final testing.

Nominal 80% uncertainty uses per-method absolute calibration residuals normalized by the preceding four-week mean, floored at ten units. Frozen empirical quantile radii scale later forecasts, with lower bounds clipped at zero. Serial dependence, cohort changes and final refitting prevent a coverage guarantee. [ML methodology](ML_METHODOLOGY.md) and the [model card](MODEL_CARD.md) document these assumptions and native-importance limitations. Optional MLflow is deferred; local JSON/Parquet/joblib tracking stores seed, features, split roles, configurations, candidates, metrics, source/runtime/code hashes, timestamps, timings and Git hash when available.

Training validates source coverage and publishes `artifacts/phase3/<experiment_id>/` atomically. Before any final-test claim, evaluation preflight checks the frozen plan, configuration, all six methods, cohort/calibration metadata, model hashes, protocol code/runtime identities and matching source identity. `data/evaluation-ledger/<dataset_id>.json` is reserved exclusively immediately before semantic test-target access. Interrupted claims remain blocked for explicit investigation; an alternate experiment cannot reuse that dataset reservation. Successful evaluation publishes `artifacts/phase3/evaluations/<experiment_id>/`, marks the ledger complete and permits hash-verified cache reuse without reloading test targets. The local ledger requires a trusted stable workspace; deleting or changing its root defeats a cooperative file guard and is not a valid retuning workflow.

The official final test is complete. Ridge was fixed from selection-validation WAPE (53.52% versus the four-week mean's 60.22%); final-test WAPE was 52.75% for Ridge versus 51.97% for that baseline. ML therefore failed to beat the best baseline on this final test. The selected recommendation is not revised or tuned from this observation. Phase 4's separate simulated policy comparison below does not change this forecasting result or establish real company savings.

## Completed inventory pipeline (Phase 4)

[Inventory methodology](INVENTORY_METHODOLOGY.md) fixes timing, defaults, information limits, five policies, empirical error estimates and finite-horizon accounting. Inputs remain separate: recorded gross purchases as historical simulated demand; already-issued frozen Phase 3 predictions; illustrative business assumptions; and simulated stock/fulfillment/cost outcomes. Original inventory, purchase costs and true unmet demand are unavailable.

`InventoryParameters` and `InventoryState` validate finite assumptions, whole-unit stock/lead/review/MOQ/pack/capacity fields and exact quantity arithmetic within `2^53-1`. The planner computes inventory position, flat carry-forward lead demand, normal-approximation safety stock, reorder point and protection target. At a review, it orders only at/below the reorder point; positive requests meet MOQ and pack rounding before capacity reserves on-hand plus every outstanding unit. Capacity can reduce an order to zero rather than violating MOQ. Fixed thresholds can be explicitly overridden together; target must be at least reorder point.

Weekly simulation receives arrivals before demand, fulfills available inventory, loses unmet units, records ending stock/costs and then reviews/orders. An end-week order with lead `L` arrives before demand in `t+L+1`; lead demand covers `L` weeks and the target covers `L+R`. Decisions can use only the next-origin forecast, never later-issued rolling forecasts. Because no validated multiweek model exists, horizon demand explicitly carries that one available forecast forward flat. No final-week order is placed, and later-due pipeline remains valued.

Five policies receive identical demand, initial stock/pipeline and economic inputs: previous-demand ordering, four-week-mean ordering, fixed reorder point, validation-selected ML with safety stock, and a matched moving-average safety-stock controller. Initial stock defaults to twice the 44-week pretest mean, rounded up. Method-specific error magnitudes use only normalized RMSE from the 200 pretest calibration observations per method. No test residual, inventory outcome or policy-cost comparison revises those estimates, model choices or default controller parameters.

The planner is rule-based, not a cost optimizer. Economic inputs affect reported revenue/costs; they do not automatically tune quantities. Service/error inputs, forecasts, stock position, lead/review periods and feasibility constraints determine orders. Comparing complete policies must not be attributed solely to point forecasts; the matched controller narrows that comparison but still has method-specific error buffers.

Costs include purchase payments at placement, ending-stock holding, lost-unit penalty and positive-order fees. Lost margin is reported separately, without adding it twice. Both gross cash cost and predeclared terminal-adjusted net inventory cost are reported. Net cost adds initial stock/pipeline value and credits ending stock/pipeline at the same purchase cost, assuming full terminal recoverability. Unit and pipeline conservation and both monetary identities are checked; fill rate and weekly no-stockout fraction are distinct from the configured normal service factor.

`configs/phase4.json` declares defaults and supports per-product parameter/initial-stock/prepaid-order overrides. `configs/phase4_lead2.json` changes the lead-time assumption. The later `configs/phase4_high_holding.json` changes holding cost to 0.10/unit/week and is explicitly exploratory after the first scenario results; it is not an untouched evaluation, retuning or a cost-optimal-policy claim. All controls and an override example are documented in the [README](../README.md#inventory-configuration).

The completed default run is `a6b3fa34d8663859368185afd5f940f9d165bde7024630e444a0cc1f99ebe967`, under `artifacts/phase4/<run_id>/`. Source/ledger hashes, scenario/runtime/code identity, derived inputs, demand, orders, weekly outcomes, recommendations, summary/report, CSV exports and three figures are published together and checked on reuse. Cold-default artifacts reproduce byte-for-byte, and the protected Phase 3/ledger files remain unchanged. Phase 4 adds no dependencies, database tables, API or dashboard.

Under default illustrative assumptions, ML's simulated net cost is GBP 194,633.74 and fill rate 96.3749%; the matched mean controller costs GBP 199,496.02 with fill rate 94.4925%. The signed matched net-cost difference is GBP 4,862.28 (2.4373%), with ML holding 65,510.875 average units versus 55,387.625. ML gross cash cost is GBP 265,044.74; terminal asset credits explain why net cost is lower. With lead time two weeks, the matched cost gap narrows to GBP 1,631.46 (0.6973%). At the exploratory holding cost of 0.10/unit/week, ML costs GBP 1,616.60 more than the matched controller. These are retrospective simulated estimates under the stated buffers, economics and full recovery assumption, not achieved company savings or a reversal of the negative Phase 3 point-forecast comparison. ## Assumptions, risks and environment

- Initial repository: empty Git working tree, no commits, on `main`.
- Inspected 2026-10-18: system Python 3.9.6; bundled Python 3.12.14 and Node 24.19.0; Git 2.39.5; Docker 29.8.0 and Compose 5.5.1. PostgreSQL binaries absent; Docker daemon initially stopped. Bundled runtimes need explicit paths because Python 3.12/Node are absent from the default PATH.
- UCI source may change or be unavailable. Store SHA-256 provenance, offer strict expected-digest verification and permit local input. XLSX parsing needs memory; record a real full-source run before claiming throughput. No cross-machine timing guarantees.
- Public source includes anonymized customer IDs; keep raw local files ignored and pseudonymize all downstream identifiers. Hashes are not proof of anonymization and no raw rows belong in reports/screenshots.
- Cancellation/return semantics are accounting signals, not matched physical returns. Nonmerchandise codes and extreme positive quantities need documented treatment; preserve unusual valid quantities and audit flags rather than trimming arbitrarily.
- Short history limits annual seasonality, holiday inference, stable uncertainty and causal interpretation. Historical prices do not supply real purchase costs or inventory levels.
- Separate chronological calibration reduces selection reuse, but pooled residuals transfer across products and to refitted models; nominal intervals remain empirical. Final-test observations cannot be reused for model/parameter selection or interval adjustment. Preserve completed artifacts and the dataset ledger when relocating the project.
- Inventory assumptions are illustrative; purchases underrepresent unknown unmet demand. Normal/square-root safety stock assumes stable independent errors, lead/review forecasts use flat carry-forward, capacity conservatively reserves every pipeline unit, and eight-week terminal recoverability can favor held stock. Higher fill or lower assumed net cost need not mean lower cash use, less inventory or better point accuracy. Economic scoring does not automatically optimize the ordering rules.
- File publication and DB transaction cannot be one ACID operation; publish immutable verified files first, then retry idempotent metadata registration. Never claim imported DB state until its transaction commits.
- API documentation, full local application delivery and actual dashboard screenshots are complete through Phase 6. The Phase 3 model card and completed Phase 4 inventory scenarios describe actual local functionality.
